- CRM data lives in Lovable Cloud tables (accounts, leads, messages, appointments, ai_usage); the browser reads/writes through `src/lib/crm/store.tsx`. Why: one place for optimistic state + persistence.
- Bot qualification runs only in `qualifyLead` (`src/lib/crm/qualify.server.ts`, exposed via `qualifyMessage`), which applies tag/stage rules from `automation.ts` after the AI extracts data. Why: keeps AI key and pipeline automation server-side and consistent.
- Follow-up flows run server-side: DB triggers on leads/messages create enrollments and apply the anti-spam cancel; a cron-called route `/api/public/flows-tick` runs due steps via `flow-runner.server.ts` (claim lock per enrollment). The browser only polls to display progress. Why: must work 24/7 with no browser open.
- Conversation triggers (lead replies, keyword, AI intent per message, click-to-WhatsApp ad lead, AI qualification change) also enroll in the DB (`0012`): `messages_flow_enroll` runs after `messages_flow_cancel`, so anti-spam cancels before re-enrolling; `flow_try_enroll` enforces one active enrollment and `allow_reentry`. The AI intent comes from `message_intent` in `qualifyLead`, saved to `messages.ai_intent` (server only). After an inbound message the webhook calls `runDueForLead` so triggered flows answer without waiting for the cron. Why: a reply-driven flow is worthless a minute late, and enrollment must stay server-side and tenant-scoped.
- Advisor handoff (`0013`): flow steps `assign` (RPC `assign_lead`, round robin by `account_memberships.last_assigned_at`, skips `available = false`, service role only) and `notify` (rows in `notifications`, readable only by their user; optional WhatsApp to the member's personal number via `sendInternalWhatsApp`, body uses `leads.ai_summary` written by `qualifyLead`). An `asesor` message pauses the bot when `accounts.auto_pause_bot` and logs to `lead_events`; it also sets `flow_enrollments.advisor_replied` for the `advisor_replied` condition. Why: the handoff must work without the browser and never cross accounts.
- WhatsApp rules in flows (`0014`): a message step sends free text only inside Meta's 24 h window (last `lead` message); outside it uses the step's approved template (`whatsapp_templates`, synced from Meta by `syncWhatsAppTemplates`, read-only for the browser) or is skipped and logged to `lead_events`. Simulated leads/accounts without a channel skip the window check. `businessHours` steps wait for `nextOpening(accounts.business_hours)` and retry the same node. Opt-out (`leads.opted_out_at`) is set by DB triggers on opt-out phrases or AI intent `pide_baja`, by the `opt_out` action or by hand; the DB then cancels every enrollment, forces `bot_active = false` and blocks new enrollments. Why: Meta rejects free text after 24 h, and a lead who asked to stop must never get another automatic message.
- Library uploads go to the private `materials` bucket and are shared via long-lived signed URLs. Why: workspace blocks public buckets.
- WhatsApp Cloud API credentials live in `whatsapp_channels` (service-role only, no client grants); all sends go through `dispatchMessage` in `whatsapp.server.ts`, which falls back to simulation when no enabled channel exists. Incoming messages hit `/api/public/whatsapp/webhook` (Meta HMAC signature with the account's App Secret), are stored once as `pending` and answered by `processInboundMessage` in `inbound.server.ts` (DB claim `claim_inbound_message`: one message per lead, max attempts, no reply for accounts without owner; `flows-tick` sweeps retries). Why: tokens never reach the browser, one send path for bot, flows and advisors, and Meta retries never cause double replies.
- Bot AI: `runQualifier` (`ai.server.ts`) routes `anthropic/*` models to `claude.server.ts` (official `@anthropic-ai/sdk`, secret `ANTHROPIC_API_KEY`, structured output from `qualificationSchema`); other models go through the Lovable gateway. Only the server writes `lead`/`bot` messages; the browser can only insert `asesor`. Why: one qualification schema for every provider, and no forged history.
- Tenant isolation: every table is scoped by `account_memberships` (RLS in `0008`). Security tests: `npm test` (webhook, AI queue, credentials) and `npm run test:db` (RLS on a disposable local Postgres). Why: a policy regression must fail a test, not reach a customer.
- Flow JSON (import, export, AI drafts) always goes through `parseFlow` in `flow-io.ts`; AI drafts come from Claude via `generateFlowDraft` and open in the editor unsaved. Why: one validator for every untrusted flow source.
- Visual system: glass/lift/press utilities and hairline/shadow tokens live in `src/styles.css`; `.bg-card` surfaces get frosted glass globally; theme (light/dark/system) is a `dark` class on <html> set by an inline head script + `ThemeToggle`. Why: restyle once at the token level instead of per component.
